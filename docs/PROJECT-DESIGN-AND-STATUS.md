# 实施项目管理平台：完整设计与开发状态

> 文档基线：2026-07-28  
> 当前开发分支：`fix/round1-technical-audit`  
> 系统版本：`1.1.0`

## 1. 产品定位

本系统面向医疗信息化实施团队，用于统一管理从项目立项、实施计划、任务执行、问题闭环、交付物审核、上线验收到知识沉淀的完整过程。平台的核心目标是把分散在聊天、表格、文档和个人经验中的实施过程转化为可追踪、可审计、可复用的数据。

主要使用角色：

- 管理员：管理用户、角色、全平台配置和全部项目数据。
- 项目经理：创建并管理自己的项目、计划、成员、任务、问题和交付物。
- 项目成员：访问已加入项目，执行任务、提交进展和处理问题。
- 开发人员：处理研发任务、缺陷及接口联调事项。
- 只读用户：查看被授权项目和报表。

## 2. 业务范围

### 2.1 项目管理

- 项目创建、编辑、查看与安全删除。
- 项目负责人、客户、阶段、计划上线日期、健康度和进度管理。
- 项目成员关系控制数据访问边界。
- 项目启动、暂停、恢复和结项生命周期。
- 结项前校验未完成任务、未关闭问题及未完成审核的必需交付物；存在阻塞项时返回 HTTP 409 和各类阻塞数量。

### 2.2 SOP 与实施计划

- 维护实施 SOP 模板、阶段和任务。
- 根据工期自动计算阶段及任务权重。
- 从 SOP 生成项目实施计划，并支持合并同步。
- 计划任务与业务任务关联，任务进度回写项目计划。
- 检查项完成度驱动任务实际进度和状态。
- SOP 写操作受 `sop.create`、`sop.edit` 或管理员角色控制。

### 2.3 任务与问题

- 创建、编辑和更新任务状态、进度及计划日期。
- 维护问题类型、等级、责任人、截止日期和闭环状态。
- 普通用户只能访问其所属项目的数据。
- 支持禅道任务同步记录；外部禅道接口需配置独立凭证后启用。

### 2.4 消息采集与确认

- 支持人工消息、每日进展卡片及受限机器人入口。
- 人工消息和每日卡片必须归属真实项目，并在写入前校验项目成员权限。
- 机器人尚无独立签名鉴权，目前仅管理员可调用；管理员可创建未归属消息。
- 消息列表按当前用户可访问项目过滤；未归属消息仅管理员可见。
- 消息确认使用单个 MySQL 连接和事务，通过 `SELECT ... FOR UPDATE` 锁定消息。
- 结构化结果经统一校验后才能生成任务或问题；没有结构化结果时仅确认消息。
- `generated_task` 和 `generated_issue` 标记用于保证重复确认不重复生成业务数据。
- 任意写入失败回滚整个确认事务。
- JSON 消息文件回退已经移除，消息业务必须使用 MySQL。

### 2.5 文档与交付物

- 文档关联项目、实施计划任务和交付物。
- 支持上传、下载、编辑、审核和删除。
- 文件保存成功而数据库插入失败时删除已保存对象，避免孤儿文件。
- 删除流程先完成数据库事务，再删除对象；对象删除失败记录补偿错误。
- 已审核项目文档可沉淀到知识库。

### 2.6 知识库

- 知识分类、文章、附件和来源项目/文档关联。
- 草稿、待审核、发布、驳回等状态流转。
- `knowledge.view/create/edit/review/delete` 权限控制。
- 支持标准知识和项目沉淀两类来源。

### 2.7 报表与审计

- 项目驾驶舱汇总项目、延期任务和风险数据。
- 周报按当前用户可访问项目统计，普通用户不能获取全平台数据。
- 审计日志直接接收当前请求用户和请求 IP，不使用全局可变上下文。
- 审计数据库写入失败必须记录错误，不静默吞掉异常。

## 3. 系统架构

当前系统采用轻量单体架构：

```text
浏览器单页界面 index.html
          │ HTTP/JSON
          ▼
Node.js 原生 HTTP 服务 server.js
  ├─ auth.js：登录、JWT 签发与校验
  ├─ permissions.js：动态角色权限加载
  ├─ message-result.js：消息结构化结果校验
  ├─ storage.js：文件对象存储适配
  └─ db.js：MySQL 连接池
          │
          ├──────── MySQL 业务数据
          └──────── 本地/挂载目录文件对象
```

技术栈：

- 前端：单页 HTML、CSS、原生 JavaScript。
- 后端：Node.js 原生 `http` 模块，CommonJS。
- 数据库：MySQL 8，`mysql2/promise` 连接池。
- 身份认证：账号密码、bcrypt、JWT、HttpOnly Cookie。
- 文件存储：`storage.js` 适配层，当前默认本地持久化目录。
- 部署：Dockerfile、Docker Compose、Windows 部署脚本。
- 测试：Node.js 内置 `node:test`。
- CI：GitHub Actions 执行 `npm ci`、语法检查和自动化测试。

### 3.1 请求处理顺序

1. 健康检查和认证配置等公开端点先处理。
2. 登录接口校验账号密码并签发会话 Cookie。
3. 受保护请求校验 JWT。
4. 每次请求根据 `user.sub`、`user.role` 从数据库重新加载当前有效权限，避免长期信任 JWT 中的旧权限。
5. MySQL 核心路由执行项目成员和功能权限校验。
6. 写操作完成后记录用户、IP、对象及操作详情。

## 4. 权限模型

权限由角色和权限码组成，用户记录保存角色键，角色权限由 `roles` 和 `role_permissions` 管理。

- `admin` 通过 `['*']` 获得全权限。
- 其他角色每次请求从数据库加载有效权限。
- 项目级数据同时受功能权限与 `project_members` 成员关系约束。
- 项目经理保留创建自己项目的能力。
- 未归属消息等无法建立项目边界的数据默认仅管理员可操作。

权限判断原则：先鉴权、再授权、最后写入；403/400 返回前不得产生业务数据。

| `projects` | 项目主数据及生命周期 | 成员、任务、问题、文档、消息 |

| `issues` | 问题与风险 | 项目 |
| `documents` | 项目交付文档元数据 | 项目、计划任务、对象存储 |
| `messages` | 采集消息及生成标记 | 项目、任务、问题 |

## 6. 一致性与安全设计

- 项目结项采用后端强制校验，前端状态不能绕过。
- 消息确认使用事务与行锁，确保任务、问题、消息状态原子提交。
- 文档上传采用文件补偿删除；文档删除采用数据库优先和错误补偿日志。
- 数据库结构变更只允许在 schema 或迁移脚本中执行，业务请求期间不执行 DDL。
- 服务启动校验 `schema_migrations`；缺少 `round1-technical-audit` 时明确提示执行 `npm run db:migrate-round1`。
- MySQL 是业务服务的必需依赖；JSON 文件不再作为消息业务回退方案。
- Cookie 使用 HttpOnly、SameSite=Lax；HTTPS 部署时通过配置启用 Secure。
- 密码只保存 bcrypt 哈希，JWT 密钥和数据库密码从环境变量读取。

## 7. 部署设计

### 7.1 本地或服务器部署

1. 配置 MySQL 与 `.env`。
2. 安装依赖：`npm ci`。
3. 初始化正式结构：执行 `database/schema.sql`。
4. 执行审计迁移：`npm run db:migrate-round1`。
5. 创建管理员：`npm run db:seed-admin -- <账号> <密码> [显示名称]`。
6. 启动：`npm start`。

### 7.2 Docker 部署

- Docker Compose 负责 MySQL 健康检查和服务依赖顺序。
- 应用容器启动顺序为：迁移 → 确保管理员 → 启动服务。
- 数据库和上传目录需挂载持久卷。
- 生产环境应置于 HTTPS 反向代理后，并启用安全 Cookie。
